I containerized the entire project using Docker and orchestrated it with Docker Compose. The environment consists of three main services that communicate over a custom bridge network called edutrack-network:

Backend: A FastAPI server (Python).

Frontend: A React/Vite Single Page Application served by Nginx.

Jupyter: A Data Science environment for notebooks.

To avoid port conflicts with other applications on my Mac, I configured custom port mappings for the host machine.

2. **Backend Setup (FastAPI)**
   For the backend, I used the python:3.11-slim image to keep the container lightweight.

Key configurations I made:

Clean Dependencies: I cleaned the requirements.txt file to remove all local Mac-specific paths (like file:///AppleInternal...) to ensure it installs correctly inside the Linux container. I also pinned bcrypt==3.2.2 to avoid version conflicts with passlib.

Data Persistence: I created a volume mapping ./data:/app/data. This ensures that the SQLite database (edutrack.db) and CSV files are saved on my local hard drive. If the container stops or is deleted, I do not lose any data.

Absolute Database Path: I updated the database URL to use an absolute path (sqlite:////app/data/edutrack.db with four slashes) so SQLAlchemy always finds the database in the right folder.

Automated Entrypoint: I wrote a custom entrypoint.sh script. When the backend container starts, this script automatically:

Runs database migrations (alembic upgrade head).

Checks if the database is already seeded by looking for a .seeded lock file.

If not, it automatically runs the Python scripts to generate 1,000 students, seed the database, and create the test users.

Finally, it starts the FastAPI server.

3. **Frontend Setup (React & Nginx)**
   I used a multi-stage Docker build for the frontend to maximize performance and security.

Stage 1 (Build): Uses a node:20-alpine image to install npm packages and compile the React application (npm run build). I used Docker build arguments (ARG) to inject the VITE_API_BASE_URL during the build process so the frontend knows how to contact the backend.

Stage 2 (Serve): Uses an nginx:stable-alpine image. It copies only the compiled static files from Stage 1. This makes the final image very small and fast.

React Router Fix: Because React is a Single Page Application (SPA), I created a custom nginx.conf file. This configuration uses try_files $uri $uri/ /index.html; to make sure users don't get a "404 Not Found" error when they refresh a page (like /settings).

4. **Jupyter Notebook Setup**
   To perform Data Science tasks, I added a jupyter service using the official jupyter/scipy-notebook:latest image.

Volumes: I mapped two volumes: one for ./notebooks and one for ./data. This allows me to edit notebooks in the browser, read the CSV files generated by the backend, and have everything saved safely to my Mac.

Security: I set a fixed environment variable (JUPYTER_TOKEN=edutrack_secret) so I can easily log in without having to check the terminal logs for a random token every time.

5. **How to Run the Project**
   Here are the commands I use to manage the Docker environment:

Bash

# Build and start all services in the background

docker-compose up --build -d

# View the logs (useful to watch the automated database seeding)

docker-compose logs -f backend

# Stop the containers

docker-compose down
Access URLs:

Backend API (Swagger): http://localhost:8080/docs

### 6. Deployment Architecture & Azure Infrastructure

Following local containerization, I migrated the project to a cloud environment to ensure it was accessible over the public internet. I selected Microsoft Azure as the cloud provider and provisioned a Linux Virtual Machine (VM).

#### Infrastructure Provisioning

1. **Virtual Machine Setup:** I created an Azure Virtual Machine running Ubuntu 24.04 LTS (Standard B2ats v2: 2 vCPUs, 1 GiB memory) named `edutrack-server`.
2. **Network Security Group (NSG) Configuration:** To allow external traffic to reach the application, I configured the inbound security rules on the Azure portal. Initially, only SSH (port 22) was open. I appended rules to allow inbound TCP traffic on custom ports required by my Docker Compose setup:

- Port `3000` (Frontend Nginx server)
- Port `8000` (Backend FastAPI server)
- Port `8889` (Jupyter Lab environment)
- Port `8080` (Jenkins CI/CD server)

3. **Host Environment Preparation:** I connected to the VM via SSH using an Ed25519 private key (`.pem`). Once authenticated, I prepared the Ubuntu environment by installing fundamental dependencies, specifically `docker.io`, `docker-compose-plugin`, and `openjdk-17-jdk` (a prerequisite for Jenkins). I also added the `azureuser` to the `docker` group to execute commands without requiring `sudo` escalation.

### 7. Continuous Integration & Continuous Deployment (CI/CD) with Jenkins

To automate the deployment pipeline, I installed and configured Jenkins directly on the Azure VM. The objective was to trigger an automatic code pull, rebuild, and deployment sequence whenever new commits were pushed to the `develop` branch on GitHub.

#### Jenkins Pipeline Configuration (`Jenkinsfile`)

I authored a declarative `Jenkinsfile` stored in the root of the repository. The pipeline was structured into three primary stages:

1. **Checkout:** Clones the latest code from the GitHub repository into the Jenkins workspace.
2. **Build:** Copies the production `.env` file into the backend directory and executes `docker-compose build`.
3. **Deploy:** Uses the `sshagent` plugin to authenticate back into the Azure VM, pull the latest code to the production directory (`/home/azureuser/edutrack`), and restart the containers using `docker-compose down` followed by `docker-compose up -d`.

_Note: A 'Test' stage utilizing `pytest` was initially drafted but was bypassed (commented out) in the final pipeline because the test suite directory was not fully populated, preventing pipeline failure._

### 8. Challenges Encountered & Resolutions

The deployment phase presented several technical hurdles, primarily related to limited server resources and authentication barriers.

#### Challenge 1: Jenkins GPG Key Rotation Issue

During the Jenkins installation on Ubuntu 24.04, the package manager (`apt`) threw a `NO_PUBKEY` error. Jenkins had rotated their GPG keys, and the standard repository was unverified.
**Resolution:** I bypassed the `apt-key` manager and manually downloaded the updated `.key` file from `pkg.jenkins.io` using `curl`. I then dearmored it into a `.gpg` format and explicitly pointed the `sources.list.d` configuration to this specific, trusted keyring file.

#### Challenge 2: GitHub Authentication in Automated Pipeline

During the 'Deploy' stage, the pipeline failed with `fatal: could not read Username for 'https://github.com': No such device or address`. Jenkins was attempting to execute `git pull` on the VM but was blocked because GitHub requested interactive credential input, which is impossible in a headless automated script.
**Resolution:** I established a persistent credential store on the Azure VM. I connected to the server via SSH, navigated to the project directory, and executed `git config credential.helper store`. I then performed a manual `git pull`, providing my GitHub Personal Access Token. This cached the credentials locally, allowing subsequent Jenkins pipeline executions to pull code silently and autonomously.

#### Challenge 3: Disk Space Exhaustion (Error 28)

The most severe issue occurred during the Docker image compilation phase, resulting in `[Errno 28] No space left on device`. The Azure VM was provisioned with a 30GB disk. The Python `requirements.txt` included `torch` (PyTorch). By default, `pip` attempts to download the NVIDIA CUDA variants of PyTorch, which exceed 2.5 GB in size. During the extraction process, this expanded to over 10 GB, completely saturating the root partition and failing the build.
**Resolution:**

1. **System Cleanup:** I initiated an aggressive cleanup of the VM, stopping all services and executing `docker system prune -a --volumes -f` and `docker builder prune -a -f` to eliminate dangling images and corrupted cache layers, reclaiming approximately 14.4 GB of space.
2. **Dependency Optimization:** Recognizing the VM lacked a GPU, installing CUDA libraries was unnecessary overhead. I modified the `backend/requirements.txt` by appending `--extra-index-url https://download.pytorch.org/whl/cpu` to the very top of the file. This explicitly instructed `pip` to source the CPU-only variant of PyTorch, reducing the download payload from 2.5 GB to approximately 180 MB.

#### Challenge 4: API Connection Refused on Cloud Deployment

Once the containers were running on Azure, the frontend application loaded but failed to authenticate users, returning `net::ERR_CONNECTION_REFUSED` in the browser console. The frontend was still attempting to contact the backend at `127.0.0.1:8000`.
**Resolution:** The frontend `.env` file containing the production IP address was listed in `.gitignore` (for security best practices) and was therefore not transmitted to the server via GitHub. To rectify this without exposing secrets, I modified the fallback parameter in the `frontend/src/services/api.js` file:
`baseURL: import.meta.env.VITE_API_BASE_URL || 'http://68.221.161.128:8000/api/v1'`
After pushing this change and triggering a final Jenkins build, the frontend successfully established communication with the backend API.

#### Challenge 5: Inefficient Pipeline Build Times

Initially, the `Jenkinsfile` utilized the `--no-cache` flag during the `docker-compose build` stage. This forced Docker to re-download and recompile all dependencies on every commit, extending build times to over 15 minutes.
**Resolution:** I removed the `--no-cache` flag. Docker successfully utilized layer caching. Subsequent pipeline executions recognized the unchanged `requirements.txt` and `package.json` files, reducing the build duration from 15 minutes to mere seconds. Furthermore, I eliminated a redundant `--build` flag from the `docker-compose up` command in the Deploy stage, preventing the system from attempting to compile the images twice in one run.
